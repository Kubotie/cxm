# 02. ホーム（/v2）と提案準備ボード（/v2/readiness）

---

## A. ホーム `/v2`

実装: `src/app/v2/page.tsx`（Server, metadata のみ）→ `src/app/v2/home-view.tsx`（Client, 590 行）

### A-1. この画面の役割

ログイン直後の着地点。**「今日どこから手をつけるか」を 30 秒で決める**ためだけにある。

置く / 置かないの基準がコードコメントに明記されている:

- 置く … 毎朝見る価値があり、かつ**その場で行き先が決まる**もの
- 置かない … 個社を精査しないと意味が出ないもの（＝提案準備ボードと個社ページの仕事）

**ホームでは重い計算をしない。** 読むのはバッチが書いたものだけ。

### A-2. データ源

| 表示 | 取得元 | 元データ |
|---|---|---|
| 業界ニュース・バッチ更新状況 | `GET /api/home/digest`（`revalidate = 300`） | 週次バッチが書いた `industry_intel_cache`、日次バッチが書いた `project_metrics` |
| レーン件数・今日の要対応・利用の異変 | `GET /api/companies/proposal-board` | 提案準備ボードと同一。二重に計算しない |
| 挨拶の氏名・担当フィルタ | `GET /api/user/profile` | `staff_identify` |

3 本を独立に fetch し、それぞれ個別に loading / error を出す。

### A-3. 画面構成

```
┌ ヘッダー（sticky）────────────────────────────────────────┐
│ おはようございます、○○ さん   [自分の担当|全社] [提案準備ボード→] │
│ 9月2日(火) ・ Tier 1–3 / N社 ・ 自分の担当のみ                │
│ ● 利用データ（日次） 2026-09-02 05:31 / 1,295PJ              │
│ ● 業界ニュース（週次） 87/102社取得 ・ 7日以内 41社            │
└──────────────────────────────────────────────────────────┘
[更新を確保する N社][提案できる N社][条件付き N社][足元を戻す N社]  ← 全部 /v2/readiness へのリンク
┌─────────────────────────┬──────────────────┐
│ 担当顧客の業界で起きていること │ 今日から手をつける   │
│ （企業ラウンドロビンで混ぜた   │ 利用の異変（3タイル） │
│  ニュース最大 120 件）        │ データの更新        │
└─────────────────────────┴──────────────────┘
```

### A-4. 表示ルール（実装上の判断が入っている箇所）

- **鮮度チップをヘッダー直下に置く。** バッチが落ちた日に黙って古い数字を出すのがいちばん危ないため、画面下部ではなくヘッダー直下。今日の集計が入っていなければ amber、`coverage.failed > 0` なら赤で「業界調査エラー N社」。
- **担当フィルタの既定は「自分の担当のみ」。** `profile.name2` と `companies.owner_name` を突き合わせる。
  - **担当顧客が 0 社の人（企画・マネジメント）が開くと全部空になる**ため、その場合だけ自動で全社に切り替え、「担当顧客が登録されていないため全社を表示しています」と理由を出す（黙って切り替えない）。
- **今日の要対応**（最大 8 件）: ① `lane === 'renewal'` を満了日昇順（期限が動かせない）→ ② `lane === 'hold'` を準備度の低い順。
- **利用の異変**: `moduleVerdict === 'dormant'`（休眠）、`campaign.activity === 'stopped'`（施策停止）、`pvRate >= 90`（PV 枠逼迫）の 3 タイル。休眠は上位 4 社を企業リンク付きで列挙。
- **業界ニュースは企業ラウンドロビン。** 素直に日付順にすると 1 社の 4 件が上位を占め、「担当顧客の業界で何が起きているか」を眺める用途に使えなくなるため、企業ごとのキュー（各社最大 4 件、新しい順）を 1 件ずつ回して混ぜる。
- 業界セレクトは**絞り込み後に実在する業界だけ**を選択肢にする（空の選択肢を出さない）。
- ニュース 1 件は `企業名 / 業界 / YYYY年M月時点 / 本文 / 出典リンク` の形。出典が開けない・時点が特定できないものは取得段階で除外済み（→ [06](06-data-sources-and-cache.md) の出典ポリシー）。

### A-5. `/api/home/digest` の中身

- `fetchAllStoredIndustryIntel(500)` / `fetchMetricsBatchStatus()` / `fetchCompaniesByTiers([1,2,3], 600)` を並列取得（すべて `.catch` で握って部分表示を許す）。
- **ここで Web 検索にフォールバックしてはいけない**（1 社 85 秒）。未取得は `coverage.missing` として件数で返す。
- 返す `coverage`: `target`（Tier1–3 社数）/ `stored` / `fresh`（7 日以内）/ `missing` / `failed` / `latestAt` / `oldestAt`。
- 返す `batch.daily`: `latestDate` / `computedAt` / `rowCount` / `isToday`。

## B. 提案準備ボード `/v2/readiness`

実装: `src/app/v2/readiness/page.tsx` → `board-view.tsx`（Client, 651 行）
データ: `GET /api/companies/proposal-board`（`maxDuration = 60`）

### B-1. この画面の役割

Tier 1/2/3 の担当顧客を「今どこに提案できるか / どこは提案してはいけないか」で並べ、**今週どこを見るかを決める**。
**一覧に徹する**（2026-08-22 の方針変更）。当てる WHAT の候補・状況チップ・カタログの状態は個社ページの「提案準備」タブへ移した。一覧に判断材料と作業を同居させるとカードが縦に伸び、絞り込みができなくなるため。

### B-2. 4 レーン

| レーン | 表示名 | 意味 | 判定 |
|---|---|---|---|
| `renewal` | 更新を確保する | 解約判断が行われる満了 91〜31 日前で足元が固まっていない。新提案は持ち込まない | `renewalBucket === '31-90'` かつ `play === 'rebuild'` |
| `ready` | 提案できる | 足元が固まっている。外部で「今提案する理由」を掴めば拡張提案へ | 準備度 `high`（70 以上） |
| `conditional` | 条件付き | 提案はできるが、新規購入を求める前に足元の課題に触れる | 準備度 `medium`（45 以上） |
| `hold` | 足元を戻す | 提案の局面ではない | それ以外 |

**契約満了 30 日以内（`0-30`）は緊急ではない。** 満了 30 日以内は解約できない運用ルールのため「更新予定」（灰色）として扱い、実際に解約判断が行われる `31-90` を「更新判断期」（amber）として最も強く出す。`expired` は赤。

### B-3. カード 1 枚の情報

```
┌ T1  ○○株式会社                                   82 ┐  ← 準備度（0-100）
│ 担当名  ¥1,200,000  接点 12日前  更新 2026-11-30 [更新判断期]
│ ▁▃▅▇ 利用充足 78 / 実行体制 65 / 関係の温度 90 / 摩擦の少なさ 85
│ 施策 7（30日 0）  分析 226  PV 38%  運用 2人  習慣化なし  有料PJ 3
│ [30日: 休眠] [Experience 未使用]
│ [未解決サポート 8件] [放置運用（30日 公開0本 / 最終 214日前）] …
│ ↗ 外部機会を掴めば 拡張提案 へ
│ ▽ 未解決の摩擦が大きいため上限 45 を適用
└ → /v2/companies/[uid]?from=readiness
```

- **施策は在庫数なので必ず 30 日の公開本数を併記する。** 実測で「稼働 5 本以上なのに 30 日間 1 本も公開していない」有料 PJ が 48 件あった。
- **分析は 30 日の実測 PV。** 累計ヒートマップ数は表示しない（今使っているかが分からないため）。
- ブロッカーは最大 4 件表示 + 残数。すべて実測値をラベルに載せる（値のないラベルは、スコアが高いときに矛盾して見えて理解できないため）。

### B-4. フィルタと凡例

- Tier トグル（T1/T2/T3、全部外すと自動的に全選択に戻る）、担当セレクト、フリーワード検索（顧客名・担当）。
- **凡例パネル**（折りたたみ）に、準備度 4 要素の定義・重み・低いときの意味、カードの数字の出所と注意、30 日の利用判定 6 種、上限がかかる条件、ブロッカー 12 種の条件と理由を掲載。
  - 文言は `FACTOR_META` / `USAGE_METRIC_META` / `READINESS_CAP_NOTE` / `BLOCKER_META` / `VERDICT_META` から読む。**UI に書き写さない**（配点を直したときに説明だけ古くなるのを防ぐ）。
  - 「スコアが高いのにフラグが出る」を矛盾と読まれないための注記（`BLOCKER_VS_SCORE_NOTE`）も凡例に出す。
- 末尾に「この一覧では評価していないもの」（API の `notEvaluated`）を明示:
  - 「他ツールで代替可能」の認知（議事録の読解が必要 — 個社ページで評価）
  - 直近 90 日の接点件数（一覧では最終接点日のみ）
  - 部門別の準備度（一覧は会社単位の粗い指標）
  - 議事録からの外部シグナル抽出（一覧は登録済みの外部情報のみ）
  - アクティブユーザー数の推移（H4）— 履歴を保持していないため未実装

### B-5. `/api/companies/proposal-board` の処理

1. `fetchCompaniesByTiers([1,2,3], 600, owner?)`。
2. 並列で `最新スナップショット` / `30日前スナップショット` / `プロジェクト一覧` / `最終接点日` / `外部シグナル` を取得。
3. 全企業の**有料 PJ ID をまとめて** `loadProjectFacts()`（事前計算優先、カバー率 50% 未満なら CSV へフォールバック）。
4. 企業ごとに:
   - 有料 PJ の signal を**合算**して疑似 signal を作る（代表 1 件方式だと PV 消化率が「どの PJ を代表に選ぶか」で数十%ぶれるため）。PV 集計期間は「最も進んでいない期間」を採る（早すぎる判定を避ける安全側）。
   - モジュール判定を企業単位に畳む（`mergeModuleVerdicts`）。
   - 運用人数は**有料 PJ 横断でメールアドレスを重複排除**して数える（PJ ごとに足すと複数 PJ を見ている 1 人が人数分に膨らむ）。
   - 施策シグナルを合算（`mergeCampaignSignals`）。
   - `calcProposalReadiness(...)` → `decideProposalPlay(...)` → `decideLane(...)`。
   - 外部機会は保存済み `company_external_intel` のみで自動判定（議事録本文からの抽出は 102 社分読むと重いので個社ページ側で行う）。`?opportunity=true` で全社一括上書き可。
5. 並び順: レーン順 → 準備度降順 → MRR 降順。

**一覧版の準備度は粗い**（個社ページで精査する 2 段構成）:

- `relationship` … 全チャネルの最終接点日のみ（接点件数は取らない）。`companies.last_contact` は SF sync 由来で古いことがあるため実ログの最終日を優先。
- `friction` … `open_support_count` のみ。代替可能性の認知は未評価。
- `utilization` … 企業内の有料 PJ 合算。
- `execution` … スナップショットの会社合計（最新 vs 30 日前）。
