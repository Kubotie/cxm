# 10. 既知の制約・落とし穴・未実装

実装コメントに「実測」として残っている事実と、現時点で解けていない問題。**この章を読まずに数字を信じないこと。**

---

## 1. データそのものの制約

| 事項 | 内容 |
|---|---|
| Metabase CSV は PV>0 の行しか持たない | 「行が無い」は欠損ではなく「管理画面に来ていない」。ただし CSV 自体が全 PJ を網羅していない（実測で 1,719 PJ 分）ため、`unevaluated` を「使っていない」と読んではいけない |
| ヒートマップの閲覧は計測外 | 顧客ドメインへ遷移するため、リスト到達までしか分からない |
| 施策の停止時刻の列が無い | 「いつ止めたか」は分からない。`PAUSED` は現在の状態であって履歴ではない |
| 施策の成果が無い | 表示回数・ゴール到達数・CVR は含まれない。**ゴール数は設定数であって達成数ではない** |
| 施策名の 24% が無題 | 施策名から組織を読むときは無題を除く（除いた件数を画面に出す） |
| DELETED 施策の 70% は一度も公開されていない | 「作って消した試行錯誤」と「配信してから消した」は別の行動。`everRan` で必ず分ける |
| 施策明細は直近 2 年 | RUNNING / SCHEDULED は期間外でも含む |
| `cse_tickets` は 1 チケット = 複数行 | append 書き込みのため。`source_record_id` で畳まないと件数が 2 桁膨らむ（実測 69,698 行 = 578 件） |
| `cse_tickets` の `created_at` が空の行が多い | 実測で未クローズ 705 件中 185 件。日付不明は「古い」に倒す（新しい側に倒すと摩擦が過大に出る） |
| `companies.last_contact` は SF sync 由来で古いことがある | 実ログ（`log_*`）の最終日を優先する |
| NocoDB の `limit` は最大 2000 | 超える値は黙って切り詰められる。全件はページングで |
| NocoDB フィルタ構文を encode すると全件返る | `URLSearchParams` を使わず手でクエリを組む |
| NocoDB の Number が小数を受け付けない | 公開率は 0〜100 の整数（%）で保存し、読むときに /100 する |
| `project_user_snapshots` に主キーが無い | 重複行が蓄積し、API から削除できない。upsert 更新経路が無効になっている |
| ID 形式の差 | NocoDB `company.id` は `sf_0017F...`、Metabase は `0017F...`。両形式でマップを引かないと担当者・Tier が 1 件も紐付かない |
| Notion は database ID と data source ID が別 | URL / MCP で見える `collection://…` を REST API に渡すと 404 |

## 2. 判定の限界（画面にも明示しているもの）

提案準備ボードの `notEvaluated`:

- 「他ツールで代替可能」の認知（議事録の読解が必要 — 個社ページで評価）
- 直近 90 日の接点件数（一覧では最終接点日のみ）
- 部門別の準備度（一覧は会社単位の粗い指標）
- 議事録からの外部シグナル抽出（一覧は登録済みの外部情報のみ）
- **アクティブユーザー数の推移（`H4_Health_ActiveUsersUp_L14`）— ユーザー数の履歴を保持していないため未実装**（イベント数での代用はしない）

その他:

- `execution` の推移は `company_daily_snapshot` 由来のため**会社合計**。プロジェクト単位の推移ではない。
- 代替可能性の検出は**キーワード照合による推定**。誤検知があり得るため、必ず根拠（該当箇所）を出す。
- 準備度は推定であって確定ではない。提案の可否は根拠を確認のうえ人が判断する。

## 4. 運用・設定上の注意

- **`CRON_SECRET` / `SUPPORT_BATCH_SECRET` が両方未設定だとバッチ認証がスキップされる。** 本番で未設定のまま公開すると誰でも重いバッチと LLM 課金を叩ける。
- 共有パスワード `APP_PASSWORD`（既定 `ptengine2026`）は移行のための経過措置。全員が個別パスワードを設定したら廃止する前提。
- NocoDB のテーブル ID が未設定の機能は 501 や空配列で degrade する（例: `proposal_outlines` 未設定なら骨子の保存ボタンが出ない）。
- ビルド後に dev を起動すると `.next` の混在で古いバンドルが出る。ソースと矛盾するエラーが出たら `.next` を消す。

## 5. v2 として未整備のもの

- サイドバー掲載の 5 画面以外（Actions / Support / Assets / Documents / Outbound / AI Control / 解約分析）は **ComingSoon**。実機能は旧 UI 側にあり、アーカイブメニューから開く。
- 設定画面の「表示スコープ」は旧 UI の一覧にしか効かず、「重点領域」は**保存されるだけで読み手がいない**。
- v2 画面はロールによる出し分けをしていない（`canAccess` は旧 UI の `/ops/**` 用）。
- `company_people` の CSM 評価軸は運用されておらず（担当者入力前提の設計は失敗済み）、v2 は自動観測で代替している。
- `proposal-intents` のヘッダーコメントにある「打合せ設定率」でのカード並び替えは、現在 `meetingRate = null` のため効いていない（並びは 適合度 → 一致数 → Notion B1 の既定順）。

## 6. 変更するときに壊しやすい箇所

| 変更 | 一緒に直すもの |
|---|---|
| 準備度の配点・閾値 | `FACTOR_META` の説明文（凡例の正本）。`READINESS_THRESHOLD` に集約されているのでコードは 1 箇所だが、**説明だけ古く残る** |
| ブロッカーの条件（`buildBlockers`） | `BLOCKER_META`（凡例）。1 対 1 対応を保つ |
| 状況 ID の生成 | **`signalIdsFromReadiness()` 以外で組み立てない。** 散らすとボードと個社で別判定になり原因を追えない |
| 行動シグナルの判定 | `behavior-signals.ts` に閉じる。閾値は `BEHAVIOR_THRESHOLD` |
| 事前計算のスキーマ（`project_metrics`） | `fromMetricRow()` の復元処理。**表示文言は判定ロジック側が正本なので事前計算に保存しない**（結論と数値だけ保存する） |
| Notion カタログ | CXM から書き込まない。B/C は Notion が正本、状況 ID の語彙はコードが正本 |
| AI が読めるエンドポイントを増やす | `data-sources.ts` の allowlist に**説明文つきで**追加する（説明文がツール選択の判断材料になる） |
| 個社ページのタブ追加 | `sources[].loaded` の申告を忘れると、AI が未取得のまま総合判断を書く |
