# 07. 判定ロジック（提案準備度・利用判定・シグナル・WHAT マッチング）

v2 の画面はほぼすべて、この章の計算結果を表示しているだけ。
計算は `src/lib/company/**` に閉じており、**サーバー・クライアント両対応（副作用なし）** に保たれている。

## 1. 提案準備度（Proposal Readiness）

実装: `src/lib/company/proposal-readiness.ts`
問い: **「今この顧客に提案を持ち込んでよいか」を既存データだけで判定する。**

背景: 外部トリガー（IR の DX 投資・組織変化など）を掴んでも、提供中の機能が使われていない状態で新提案を持ち込むと打診が通らない。**外部機会は消耗品であり、準備度が低いときに使うと機会そのものを焼く。**

評価単位は原則 **project（＝部門・予算単位）**。会社単位で平均すると「主契約部門は解約方向、別部門は拡張余地」のような差が消える。company スコープは一覧用の粗い指標。

### 1-1. 4 要素と重み

| 要素 | 短縮名 | 何を測るか | 重み |
|---|---|---|---|
| `utilization` | 利用充足 | 提供中の機能が実際に使われているか | 0.35 |
| `execution` | 実行体制 | 顧客側に手を動かす人がいるか | 0.25 |
| `relationship` | 関係の温度 | 打診が届く状態か | 0.25 |
| `friction` | 摩擦の少なさ | 未解決の摩擦が無いか（高い＝少ない） | 0.15 |

- 各 0〜100。**算出に必要なデータが無い要素は `null`**（推定しない）。
- overall は算出できた要素だけで重み付き平均を取り、欠損分は重みから除外して正規化する。
- レベル境界: `high >= 70` / `medium >= 45` / それ未満 `low` / 全欠損なら `unknown`。

### 1-2. ① utilization の配点

| 項目 | 配点 | 刻み |
|---|---|---|
| 稼働キャンペーン数（目標付き） | 35 | 10 本以上 35 / 5 以上 25 / 3 以上 15 / 1 以上 7 / 0 は 0 |
| **30 日の分析・検証 PV**（モジュール実測） | 25 | 110 以上 25 / 60 以上 20 / 15 以上 14 / 3 以上 8 / 1 以上 3 |
| 習慣化 | 20 | あり 20 / なし 0 / 不明 10（中間値） |
| 最終活動の鮮度 | 20 | 3 日以内 20 / 7 日 16 / 14 日 10 / 30 日 5 / それ以降 0（不明は 10） |
| PV 着地見込みが低い | −8 〜 −12 | 期間経過 25% 以上で、着地予測が契約枠の 40% 未満のとき。25% 未満なら −12 |

分析 PV の閾値は有料 PJ 1,302 件の実測分布で校正（50%tile=0 / 70%=2 / 80%=12 / 90%=58 / 95%=108 / 99%=368）。
**旧指標（累計ヒートマップ）は 95%tile でも 13 件で、分析の配点が事実上死んでいた。** 30 日実測が取れないときだけ累計ヒートマップにフォールバックする。

さらに 30 日の実測による**上限（`MODULE_CAP`）**:

| モジュール判定 | 上限 |
|---|---|
| `dormant`（30 日アクセス無し） | 20 |
| `unused`（着地画面まで） | 35 |
| `partial`（契約製品の一部が未使用） | 60 |

（実測 2026-08-22 / 有料 PJ 1,302 件: 休眠 695・未使用 88・一部未使用 69）

### 1-3. ② execution の配点

取得できた配点だけで正規化する（一部欠けても判定できる）。3 つとも取れなければ `null`。

| 項目 | 配点 | 刻み |
|---|---|---|
| 運用人数（直近 4 週に管理画面を触った**顧客側**アカウント数。社内 @ptmind.com は除外） | 40 | 4 人以上 40 / 3 人 34 / 2 人 27 / **1 人 18** / 0 人 0 |
| 稼働キャンペーン数の 30 日推移 | 50 | 増加 100% / 横ばい（±10%）76% / 減少（−30% まで）40% / 大幅減 10% |
| 30 日活動量（L30）の推移 | 30 | 同上 |

実測（2026-08-22）: 運用人数の中央値は 1 人、1,651 PJ 中 1,120 PJ（68%）が 1 人。**1 人が普通なので低く扱いすぎない配点**にし、代わりに「1 人に依存しています（担当者が抜けると止まります）」を理由文で出す。
推移は**必ず同じ集計単位**（会社合計なら会社合計）で比較する。プロジェクト個別の現在値と会社合計の過去値を比べると増減率が壊れる。

### 1-4. ③ relationship の配点

| 項目 | 配点 | 刻み |
|---|---|---|
| 最終接点からの日数 | 60 | 14 日以内 60 / 30 日 50 / 60 日 35 / 90 日 20 / それ以降 5 |
| 直近 90 日の接点件数 | 40 | 5 件以上 40 / 3 件以上 30 / 1 件以上 18 / 0 は 0 |

一覧（ボード）では接点件数を取らないため 60 点満点を正規化した値になる。

### 1-5. ④ friction の配点

| オープンサポート件数（直近 90 日） | スコア |
|---|---|
| 0 件 | 100 |
| 1〜2 件 | 85 |
| 3〜5 件 | 60 |
| 6〜10 件 | 35 |
| 11 件以上 | 12 |
| 不明 | 60（中間値） |

加えて「他ツールで代替可能 / 内製化で代替」の**認知の摩擦**を減点する。チケット 0 件でも代替判断が出ていれば摩擦は存在する。
古い言及ほど弱める: 90 日以内 −40 / 180 日以内 −15 / それ以上 0（時期不明は −40）。

### 1-6. AND 性のキャップ

平均が高くても、致命的な要素が 1 つあれば提案は通らない。

| 条件 | overall 上限 |
|---|---|
| friction < 40 | 45 |
| utilization < 25 | 50 |
| 契約満了 91〜31 日前（解約判断期）かつ準備度が high でない | プレイを `rebuild` に固定 |

適用理由は `caps[]` に入り、画面にそのまま出る。

### 1-7. 提案の型（`decideProposalPlay`）

| 準備度 × 外部機会 | 型 | 指針 |
|---|---|---|
| high × あり | `expand` 拡張提案 | 機会の文脈に沿った新しい価値を提案できる |
| high 未満 × あり | `connect` 接続提案 | 新規購入を求めず「新しい投資が決まった今こそ、既に導入済みのものを成果に変える」文脈に接続 |
| high / medium × なし | `deepen` 深化 | 現在の活用を深掘りし、成果の再現性を作る |
| low × なし | `rebuild` 立て直し | 提案の局面ではない。利用の停滞と摩擦の解消が先 |
| 更新 91〜31 日前 かつ high 未満（機会の有無を問わず） | `rebuild`（更新確保を優先） | 外部機会は更新が固まってから使う |
| 算出不能 | `unknown` | 利用実態・接点記録の取得を確認する |

**満了 30 日以内（`0-30`）にはガードレールを掛けない。** 解約できない運用ルールのため更新はほぼ確定しており、むしろ次期に向けた提案を仕込む時期になる。

### 1-8. PV 消化の判定（`pvPeriodStatus`）

**PV 枠は暦月ではなく契約更新日の応当日でリセットされる**（実測: 2026-08-18〜09-17 の期間を持つ PJ がある）。したがって消化率だけで判定してはいけない。

- 判定に必要な最低経過率 `PV_MIN_ELAPSED = 0.25`。これ未満は「期間が始まったばかり」として判定しない。
- 使う値は**着地予測**（`Month Period Pv Forecast`、BI 側で期間正規化済み）。
- 着地予測が契約枠の **40%（`PV_UNDERUSE_RATE`）未満**なら「オーバースペック」。
- 判定できない理由（上限未設定 / 期間未取得 / 経過が浅い / 実績なし）は `note` として画面のツールチップに出す。

実測例: 期間開始 5 日目で消化 2%（着地予測 12.2%）。一律 40% 未満で赤フラグを立てると始まったばかりの顧客に警告が出る。

### 1-9. ブロッカー（赤いフラグ）

`BLOCKER_META` が凡例の正本、`buildBlockers()`（proposal-board）が実装。**1 対 1 で対応させる。**

| ラベル | 条件 |
|---|---|
| 更新判断期（91〜31日前） | `renewalBucket === '31-90'` |
| 更新期限切れ | `expired` |
| 未解決サポート N件 | オープン 6 件以上 |
| 習慣化なし | 有料 PJ がどれも習慣化に到達していない |
| 稼働施策 N本 | 目標付き稼働キャンペーンが 2 本以下 |
| 放置運用（30日 公開0本 / 最終 N日前） | 稼働中の施策はあるが 30 日の新規作成も公開もない |
| 作成N本・公開0本 | 30 日で作っているのに 1 本も公開されていない |
| ゴール未設定 N本 | 配信中の施策にゴールが無い |
| 分析 NPV/30日 | 30 日の分析・検証 PV が 5 未満（モジュール未評価なら出さない） |
| PV着地見込 N% | 上記 1-8 の underused |
| 施策が減少（実行 N） | execution < 30 |
| 接点が途絶（関係 N） | relationship < 30 |

**すべて実測値をラベルに載せる。** 値のないラベル（旧「分析ほぼ未実施」）は 4 要素のスコアが高いときに矛盾して見えて理解できなかった（実測で「分析 226PV/30日」なのに「分析ほぼ未実施」が出ていた）。

## 2. モジュール利用の判定（30 日 / 契約 × 実利用）

実装: `src/lib/company/module-signals.ts`

- プラン正規化: `BUNDLE` → Insight + Experience、`PTI` → Insight、`PTX` → Experience、`FREE` / `TRIAL` / `UNKNOWN`。
- 「使っている」に**回遊（着地画面）と共通モジュールを含めない**。含めると全員が使っている扱いになる。
- 深い利用（分析・検証）の最低 PV は 5（`DEEP_PV_MIN`）。1〜2 回の偶発的閲覧を除く。

判定の分岐（上から順に評価）:

```
モジュールデータ無し
  └ L30 Active = 0     → dormant   （管理画面にも来ておらず計測イベントも0）
  └ L30 Active > 0/不明 → unevaluated（断定しない）
データ有り
  └ 回遊のみ / 実利用PV=0        → unused
  └ 契約製品に30日未使用がある   → partial
  └ 深いPV < 5                   → shallow
  └ それ以外                     → healthy
```

副産物として、提案の入口になる `opportunities` を出す:
「Experience は契約済みで未使用。追加購入なしで価値を出せます」「Experience を使っているが A/B テスト未運用」「Insight を使っているがヒートマップに到達していない」など。
`viewedPlanAsPaid`（有料ユーザーがプランページを閲覧）、`legacyLp`（提供終了プロダクトの特例提供先）も理由文に出す。

### 企業単位の合算（`aggregateModuleSignals`）

**最悪でも最良でもない**:
- 1 つでも実利用があれば `dormant` にしない（子 PJ が 1 つ休眠でも企業は動いている）
- 契約製品が 1 つでも未使用なら `partial`（提案の入口を潰さない）
- データが 1 件も取れないときは L30 合計で `unevaluated` / `dormant` を決める

## 3. 施策（キャンペーン）の判定

実装: `src/lib/company/campaign-signals.ts`

「稼働施策 N 本」は在庫数で時間の概念がない。実測（2026-08-22 / 有料 PJ）で稼働 5 本以上なのに 30 日間 1 本も公開していない PJ が 48 件、最終公開が 2023 年のものまで「施策 7 本」と表示されていた。

| activity | 条件 | 意味 |
|---|---|---|
| `active` | 30 日で作成 > 0 かつ公開 > 0 | 健全に回っている |
| `stuck` | 30 日で作成 > 0、公開 0 | 作っているが公開できていない |
| `idle_run` | 30 日の作成・公開ともに 0、稼働中 > 0 | **放置運用**（過去の施策が動き続けているだけ） |
| `stopped` | 上記以外 | 停止 |

直近 30 日のパターン（有料 PJ 579 件）: 停止 193 / 健全 188 / **放置運用 178** / 詰まり 20。

追加の介入理由: ゴール未設定の配信本数、公開率が低い（5 本以上で閾値未満）、**無題率 50% 超**（命名が整っていない＝場当たり的な運用）、A/B テスト本数。
企業単位の合算は「1 つでも動いていれば停止扱いにしない」。

## 4. 内部・行動シグナル（R\* / O\* / H\*）

実装: `src/lib/company/behavior-signals.ts`

Notion A「状況カタログ」の内部・行動層を既存データから組み立てる。
未実装だった 2026-08-21 時点では、102 社中 72 社が `PLAY_Deepen` 1 個しか持たず、WHAT の順位がカタログ登録件数という顧客と無関係な要素で決まっていた。**マッチングの解像度はここで決まる。**

| ID | 意味 | 閾値 |
|---|---|---|
| `R1_Risk_NoLogin_ConsecutiveDays` | 最終活動から離れている | 14 日以上 |
| `R2_Risk_UsageDrop_WoW` | 直近 7 日が 30 日平均の週割りを下回る | 比 0.6 未満。30 日活動量 20 件未満は母数不足で評価しない |
| `R4_Risk_TicketBurst_L7` | 直近 7 日の新規問い合わせ急増 | 3 件以上 |
| `R5_Risk_CommunicationSilent` | 接点の途絶 | 60 日以上 |
| `R6_Risk_PVQuotaNearCeiling` | PV 上限への接近 | 当月 PV / 上限 ≥ 0.9 |
| `O1_Opp_ProjectIncrease_Company` | 有料アクティブ PJ 数の増加 | 推移比較 |
| `O2_Opp_UsageExpansion_BreadthUp` | キャンペーン運用の開始・拡大 | 0 → N（近似フラグ付き） |
| `O3_Opp_HealthyScoreUp` | `overall_health` の上昇 | critical < at_risk < healthy < expanding |
| `O4_Opp_FeatureReady_NotUsed` | 契約済みで未使用の製品がある | モジュール判定由来 |
| `H1_Health_HighHabituation_60d` | 有料 PJ が習慣化に到達 | — |
| `H2_Health_FirstGuideProgress_Complete` | オンボーディング完了 | 完了日または M-Phase |
| `H3_Health_DepthScoreUp` | 1 PJ あたり活動量の向上 | 過去比 1.2 倍以上 |
| `H4_Health_ActiveUsersUp_L14` | アクティブユーザー増 | **未実装**（ユーザー数の履歴を保持していない。イベント数での代用はしない） |

原則:
1. **判定は 1 箇所に閉じる**（画面ごとにずれると追えない）
2. **評価できなかったものを黙って捨てない** — 入力が無い語彙は `missing` に理由付きで返す。「立たなかった」と「見ていない」は意味が違う
3. 閾値は `BEHAVIOR_THRESHOLD` に集約
4. 近似で代用したものは `approximate: true` を付ける

## 5. 状況 ID の組み立てと WHAT マッチング

実装: `src/lib/company/what-matching.ts`

### `signalIdsFromReadiness()` — **状況 ID を組み立てる唯一の場所**

| 入力 | 生成される ID |
|---|---|
| 準備度 4 要素が 45 未満 | `RD_Util_Low` / `RD_Exec_Low` / `RD_Rel_Cold` / `RD_Friction_High` |
| 提案の型 | `PLAY_Expand` / `PLAY_Connect` / `PLAY_Deepen` / `PLAY_Rebuild` |
| 契約更新（残日数優先） | `RENEWAL_Near_0_30`（30 日以内）/ `RENEWAL_31_60` |
| 手動登録（`company_situations`） | `AIREADY_*` / `SKILL_NoAnalyst` / `TIME_NoCapacity` / `USECASE_Unclear` など |
| 外部シグナル | `X5_Mkt_DXInvestment` など（既に状況 ID の形） |
| 行動シグナル | 上記 R/O/H |
| 事例 0 件のとき | `INDUSTRY_NoMatchingCase` |

> ⚠️ `friction < 40` → 上限 45、準備度が低い → `connect`/`rebuild` 固定 という**全体ガードレールが既に効いている**ため、`RD_Friction_High` と `RENEWAL_Near_0_30` を Notion 側の「逆効果」にも入れて二重に効かせない。

### マッチング結果

- `primary`（主役 WHAT）/ `supporting`（補助）/ `frames`（文脈フレーム）/ `excluded`（除外）/ `issues`（カタログ側の問題）。
- スコア = **一致した状況数 × 打合せ設定率**。同点のタイブレークは `effectiveTotal`（効く状況の登録総数が少ない = より特化しているものを上に）。
  これが無いと同点が名前順になり、汎用 WHAT が常に上位を占めて特化 WHAT が候補に出なくなる（実測: Ptengine Insight が全社で 3 位固定になった）。
- **`excluded` は必ず返す。**「逆効果に当たって外した」が最も価値の高い情報で、静かに消えると誰も気づけない。
- 対外呼称ルール（`applyNamingRule`）で社内語を出さない。

### 外部シグナル（X 系）

実装: `src/lib/company/external-signal.ts`

| ID | 内容 |
|---|---|
| `X5_Mkt_DXInvestment` | DX / AI 投資・予算の明記 |
| `X6_Org_NewTeamFormed` | 新部署・新体制・新サイトの立ち上げ |
| `X7_Org_ExecChange` | 担当役員・部門長の交代 |
| `X8_Org_HiringSurge` | 関連職種の採用・増員 |
| `X9_Mkt_CompetitorAdoption` | 競合ツールの導入・比較検討 |
| `X10_Mkt_StrategyShift` | 事業方針の転換 |

原則:
1. **取り込んだ瞬間に signal_id へ変換する。** 変換先が決まらない情報は取り込まない（読み物で終わらせない）
2. **出典（URL または議事録 ID）と日付が必須**
3. **鮮度で減衰する**（古い情報で提案の型を変えない）
4. キーワード抽出は推定なので必ず該当箇所（excerpt）を返し、人が打ち消せるようにする

先行性の順序（早い順）: 求人 > 組織改編 > 中計/IR > 決算 > プレス > 議事録での言及。
議事録由来は最も遅いが追加コストゼロで今すぐ取れるため第一層として使う（confidence 0.35、保存しない）。
