# 19 解約レーダー設計 v1（事前検知ダッシュボード）

> 位置づけ：既存の「解約分析」（`/console/churn-analysis`＝解約**後**の遡及）とは別系統。解約**前**に気づくための新メニュー `/v2/radar`。
> 根拠：エレコム株式会社（`sf_001Q900000tHQjBIAW`）の実データ検証（2026-09-04）。予兆は5ヶ月前から全て NocoDB に入っていたが、どの検知ロジックにも載っていなかった。

---

## 0. なぜ別メニューなのか

既存の資産は「答え合わせ」しかしていない。

| 既存 | 対象 | 出力 | 限界 |
|---|---|---|---|
| `churn-retrospective.ts` + 週次バッチ | **解約済み**企業 | d30/d60/d90 に予兆があったか | 解約後にしか動かない |
| `readiness` の `renewal` レーン | 更新91〜31日前 | 提案してよいかの判定 | 提案可否の判断が主目的。更新180日以上前は対象外 |
| `alerts`（policy_alert） | 全社 | 空白60日・意思決定者未登録 | 発火が遅い。エレコムでは意向表明とほぼ同時（2026-09-01）に鳴った |
| `overall_health` | 全社 | at_risk / critical | エレコムでは**4ヶ月鳴りっぱなしで誰も動かなかった**。v2 UI では未使用 |

**解約レーダーの役割は1つ**：更新の3〜6ヶ月前に、静かに落ちている顧客を名指しして、放置日数を可視化すること。

## 1. 設計の根拠（エレコム実測）

意向表明は 2026-09。以下は全て NocoDB に既に入っていた。

| 時期 | データ源 | 実測値 |
|---|---|---|
| 2026-01〜06 | `log_notion_minutes` | 議事録が**半年ゼロ**（2025-08〜12は月1〜2回あった） |
| 通年 | `project_user_snapshots` | `l30_active_users` が 7人中 **0〜1人**、5ヶ月継続。新規ユーザー追加ゼロ |
| 2026-05〜07 | 同上 | `running_campaign_count` が **5→4→3→2 と単調減少**（増加月ゼロ） |
| 2026-03〜09 | `csm_customer_phase` | M-Phase は `6.Engagement` なのに**習慣化率=No が半年連続**、`L60_習慣化Y_cnt`=0 |
| 2026-04-07 | `cse_tickets` | severity=high のPTX不具合。「編集操作が一切できず業務に深刻な影響」。**Waiting Confirm のまま放置** |
| 2026-07-03 | `log_notion_minutes` | 「自動更新でない方が安心だよねという話になっている」「配信されない事象…クレームにもなった」「成果が出たものは直接ソースへ書き込む」「KARTEでは見えた」 |

### 検知できなかった構造的な理由

1. **指標の定義ズレ**：企業レベルの `total_l30_active` は「30日の活動イベント数」（`project-aggregate.ts:299`）。12〜21 と出て健全に見える。PJレベルの `l30_active_users`（管理画面ログイン人数）は 1。AIサマリーも「活動イベント数は17なので比較的活発」と**逆の安心材料**を出した。
2. **単調減少を見る指標がない**：スナップショットは日々の値を持つが、「減り続けている」を判定するロジックがどこにもない。
3. **議事録が数値化されていない**：解約理由そのものがテキストで保存されているのに、どのシグナルにもなっていない。
4. **鳴りっぱなしの放置が見えない**：`at_risk` が4ヶ月続いても、UI にはその継続日数が出ない。

→ この4点を潰すことが、そのままレーダーの要件になる。

## 2. 検知モデル：3層 × 契約時計

単一スコアにしない。`overall_health` が飽和して無視された前例があるため、**性質の違う3層を分けて持ち、契約時計で緊急度を掛ける**。

### 層1：Usage decay（利用が静かに減る）— 自動・確実

| ID | 名前 | 条件 | 強度 |
|---|---|---|---|
| `D1` | 席が空いている | `l30_active_users / total_users < 0.2` が30日継続 | high |
| `D2` | 施策の単調減少 | `running_campaign_count` が60日で減少のみ、純減 ≥2 | high |
| `D3` | 習慣化が戻らない | 習慣化率=No が60日連続 | low（重み1）|
| `D4` | 席が増えない | `total_users` が90日間 変化なし、かつ D1 併発 | low |
| `D5` | 施策がピークから半減 | 180日のピーク比 50%以下 かつ 純減2以上 | medium |

**D3 を重くしない理由（実測）**：Tier1–2 の 69社中 **28社（40%）** で立つ。ほぼ全社が該当する指標に識別力は無い。単独では watch にも届かない重み1に留め、他の症状と重なったときだけ効かせる。

**D5 が要る理由（実測）**：D2 は「減っている最中」しか捉えられない。エレコムの 5→2 は5〜7月に起きたため、9月時点では60日窓が平坦になり **D2 が消えた**。畳まれた状態が続くこと自体がリスクなので、ピーク比で別に見る。

**窓カバー率**：`D1 / D3 / D4` は「窓の中の全データが条件を満たす」形なので、観測が1点しかなくても真になる。実測でスナップショット開始直後（5/1）に D1 が「0日継続」で点灯し、5/8 に critical へ達した。観測が窓の 70% を埋めていないものは `missing`（見ていない）に倒す。

※ D1 は既存 `R1`（最終ログイン日ベース）とは別物。**人数の稼働率**で見る。エレコムの見逃しはここ。

### 層2：Relationship decay（関係が冷える）— 自動

| ID | 名前 | 条件 | 強度 |
|---|---|---|---|
| `B1` | 接触空白 | 最終接点（議事録/Intercom/チケット）から60日。更新90日前以内なら**30日に短縮** | high |
| `B2` | 担当交代の直後 | `csm_customer_phase.sf_cs` が90日以内に変更、かつ B1 併発 | medium |
| `S1` | 未解決の摩擦 | severity=high チケットが14日以上 open / Waiting Confirm | high |

### 層3：Stated intent（言質）— LLM抽出 → 人が承認

議事録・Intercom 本文から、解約に直結する発言を**引用付きで**拾う。最強のシグナルだが誤検知が痛いので、必ずレビューを挟む。

| ID | 意図 | 拾う語彙の例 |
|---|---|---|
| `V1` | 自動更新の回避 | 「自動更新でない方が」「稟議」「決裁」「契約管理を厳格化」 |
| `V2` | 他社比較 | 競合名、「〜では見えた」「乗り換え」 |
| `V3` | 効果を説明できない | 「効果が特定できない」「報告のしようがない」「ROIが出せない」 |
| `V4` | 製品起因の不信 | 「クレームになった」「頼れない」「直接書き込む運用にする」 |
| `V5` | 内製化・縮小 | 「体制変更」「予算削減」「担当が離れる」 |

### 乗数：契約時計（Clock）

同じ症状でも更新30日前と300日前では意味が違う。

- 更新まで ≤30日 → ×2.0
- ≤90日 → ×1.5
- ≤180日 → ×1.2
- それ以上 → ×1.0

### ステージ判定

```
score = (D層の重み和 + B層の重み和 + V層の重み和) × Clock
critical : 承認済みの言質あり
         : または score ≥ 8 かつ 更新まで180日以内
warn     : score ≥ 8 だが更新が遠い / 更新日が不明
         : または score ≥ 4
watch    : score ≥ 2
```

**critical に「更新180日以内」を要求する理由（実測）**：critical の意味は *今週手を打つ* であって「一番悪い」ではない。この条件が無いと 69社中 12社が critical になり、その中に更新まで300日ある企業が混ざって「今週やる」が機能しなくなった。条件を入れて **6社**に絞れた。ただし**言質だけは距離を問わず critical** にする — 顧客が口に出した以上、時間の問題ではない。

**更新日が不明な企業も critical にしない**。「いつまでに」が無いものは今週の仕事にできない。

## 3. アーキテクチャ

**原則：読むときに計算しない。** 個社/usage で CSV 全件DL による遅延事故を起こしている（`csv-to-snapshot-usage-perf`）。UI は作り置きの1テーブルを読むだけにする。

```
既存（追加コストなし・5ヶ月分の蓄積済み）
  /api/batch/company-snapshot-light  (cron 03:30 JST)
      └→ company_daily_snapshot / project_user_snapshots

新規①  /api/batch/churn-radar        (cron 05:00 JST・日次)
      ├ 過去90日の snapshot 系列を読む
      ├ D層 / B層 / Clock を計算（純粋関数 src/lib/churn/radar-rules.ts）
      ├ 前日 state と突き合わせて 点灯 / 悪化 / 解消 を判定
      ├→ churn_radar_state  upsert（1社1行）
      └→ churn_radar_events append（変化のみ）

新規②  /api/batch/churn-voice        (cron 06:00 JST・週次)
      ├ 直近30日の log_notion_minutes / log_intercom / cse_tickets 本文
      ├ LLM で V1〜V5 を引用付き抽出（src/lib/prompts/churn-voice.ts）
      └→ churn_radar_voice（review_status=pending）

UI  /v2/radar
      ├ GET /api/radar/board          state を読むだけ
      ├ GET /api/radar/company/[uid]  90日時系列＋根拠＋出来事
      ├ POST /api/radar/ack           確認・対応中・様子見・誤検知
      └ POST /api/radar/voice/[id]    言質の承認 / 棄却
```

### 純粋関数として切る理由

`radar-rules.ts` は副作用を持たない（`behavior-signals.ts` と同じ設計）。理由は**バックテストを回すため**。過去のスナップショットを流し込めば、解約済み企業に対して「何日前に鳴ったか」が即座に出る。閾値はこれで決める。

## 4. データモデル（新規3テーブル）

> `project_user_snapshots` は PK 無しで重複行が蓄積している（`project-user-snapshots-no-pk`）。新規テーブルは必ず一意キーを持たせ、upsert 経路を確保する。

### `churn_radar_state`（1社1行・上書き）

| カラム | 型 | 備考 |
|---|---|---|
| `company_uid` | text | 一意キー |
| `as_of` | date | 計算日 |
| `stage` | text | watch / warn / critical / resolved |
| `score` | number | Clock 適用後 |
| `decay_score` / `blank_score` / `voice_score` | number | 層別内訳。UI で分解表示する |
| `clock_multiplier` | number | |
| `renewal_date` / `days_to_renewal` | date / number | |
| `top_reason` | text | 「なぜ今このカードが上位なのか」1文。AI ではなくルールが生成 |
| `reason_json` | json | 立った全ルールと実測値 |
| `first_detected_at` | date | **初めて watch 以上になった日** |
| `stage_changed_at` | date | |

### `churn_radar_events`（追記のみ）
`event_id` / `company_uid` / `occurred_at` / `event_type`（detected / escalated / recovered / acked / dismissed）/ `from_stage` / `to_stage` / `detail`

`voice_id` / `company_uid` / `source_type`（minutes / intercom / ticket）/ `source_record_id` / `occurred_at` / `intent_type`（V1〜V5）/ `quoted_text`（**必ず原文引用**）/ `confidence` / `review_status`（pending / confirmed / rejected）/ `reviewed_by`

## 5. UI

### 5.1 トップ ＝ スコープ `/v2/radar`

**ランキングをトップに置かない。** 健全な週も「1位＝一番危ない会社」が同じ顔で出続けると、オオカミ少年になって見られなくなる。トップは計器にして、**開いて最初に分かるべきことを「平穏かどうか」の一目**にする。

極座標のスコープ（上半円）に、点灯中の企業だけを光点で置く。

| 表現 | 対応する値 | 意図 |
|---|---|---|
| **半径** | `days_to_renewal`（中心＝更新日、外周＝1年先） | 中心に近いほど時間がない。90日以内を内側4割に厚く取り、危険圏を潰さない |
| **角度** | `decay` / `blank` / `voice` の最大層でセクターを決め、層内は company_uid のハッシュで散らす | 毎日同じ位置に出る。同じ方向に固まれば「個社でなく打ち手の問題」と分かる |
| **色** | `stage` | critical / warn / watch。健全は描かない＝**空白が平穏の表示になる** |
| **大きさ** | `mrr`（平方根スケール 3〜9px） | 失う額の大きさ |
| **明滅** | `first_detected_at` が7日以内 | 新規点灯だけ光る |
| **ゴースト** | `churn_radar_events` の先週値 | 中心に寄ってくる動きが軌跡で見える |
| **走査線** | 日次バッチの完了時刻 | 止まっていればデータが更新されていないと一目で分かる |

右側に読み取り盤：いまの判定（危険圏の社数）／新規点灯／最長放置／消灯。その下に危険圏の2〜3社だけをリストで出し、**全社の一覧は別ページに送る**（`/v2/radar/list`）。

描画は SVG。68点なら Canvas は要らず、点そのものがリンクとホバーを持てるほうが得。走査線は `transform:rotate` のみで、`prefers-reduced-motion` では静止させる。

> 参考：同じ作者の AI READY 診断が扇形の視野計で「AIから見えている範囲」を出しているのと同じ発想。**計器にすると見る動機と継続率が変わる。**

### 5.2 一覧（スコープ直下）

**別ページにはしない。** 69社なら1ページに収まり、行き来が増えるだけだった。スコープの直下に置き、`危険圏 / 点灯中 / 全社` のトグルで範囲を切り替える。並びは**更新が近い順**（同着はスコア順）— 「いつまでに」が作業の順番を決めるため。カードに必ず出すもの：

1. 会社名 / Tier / MRR / 担当
2. **更新まで残り N 日**（契約時計）
3. **なぜ今この位置なのか**を1文
4. 根拠 上位3件を**実測値つきで**（「席 1/7 が150日」「施策 5→2」「接触空白 63日」）
5. **初回点灯からの経過日数** — 長いほど帯を濃くし、「無視されている」を可視化する
6. 確認ボタン（見た / 対応中 / 様子見 / **誤検知**）

誤検知はそのまま閾値チューニングの教師データになる。

フィルタ：ステージ / 担当（自分・チーム・全体、outbound のスコープ機構を流用）/ 更新までの残日数 / 未確認のみ。

### 5.3 個社ドリル `/v2/radar/[companyUid]`

**90日を1本の時間軸に揃える**。上段に4本のスパークライン（席稼働率・施策数・接触・オープンチケット）、下段に同じ軸で出来事（議事録・チケット・担当交代・フェーズ変化・言質）を打つ。

エレコムなら「4/7 の高重要度バグ → 6月以降の施策減 → 議事録の途絶」が一目で繋がる。ここが CSM が上長・顧客に見せる資料になる。

言質カードは**原文引用と出典リンク**を必ず添える。要約だけを見せない（判断の根拠を誤らせる）。

### 5.4 精度パネル `/v2/radar/accuracy`

既存 `churn_retrospective_reports` と接続し、**解約した企業の何%を、平均何日前に検知できていたか**を出す。ルールを育てるための画面。これが無いと閾値が誰にも触れなくなる。

## 7. 決めておくこと

- **対象範囲**：Tier1–2 の CSM 担当企業のみか、有料全社（Tier3含む）か。全社だとカードが埋もれる。推奨は Tier1–2 を主動線、Tier3 は既存の `/v2/tier3` に集計値だけ出す。
- **言質抽出のモデルと費用**：週次・直近30日分に絞れば対象は数百件。`gpt-4o-mini` 相当で十分。
- **`overall_health` の扱い**：v2 では未使用のため、レーダーでも**入力に使わない**。`radar_state.stage` を新しい単一の真実にする。
